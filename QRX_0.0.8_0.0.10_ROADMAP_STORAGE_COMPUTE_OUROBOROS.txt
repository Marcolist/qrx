0.0.8 RELEASE / ACTIVATION POLICY
---------------------------------

Genesis bleibt auf dem stabilen QRX-0.0.7.7-Konsens.
Die 0.0.8-Storage-/QRX-Net-Regeln werden NICHT in die Genesis-Daten festgeschrieben.

Geplanter Ablauf:
- Genesis: 15.09.2026 mit QRX 0.0.7.7
- 0.0.8.x wird nach Genesis entwickelt, getestet und als Mandatory Update verteilt
- Ziel für die Aktivierung der 0.0.8-Funktionen: rund um den 30.11.2026
- die konkrete Activation Height wird erst nach Genesis anhand realer Mainnet-Blockzeiten festgelegt
- Consensus-Aktivierung erfolgt über den bestehenden threshold-signierten PROTOCOL_UPGRADE-Pfad
- vorgesehene Upgrade-Generation: Protocol 9
- vorgesehene Feature-Sets: DRIVE_V1 und QRX_NET_V1
- Storage-/QRX-Net-TXs sind vor Activation Height ungültig bzw. fail-closed
- alte Nodes müssen vor der Activation Height aktualisieren
- veraltete Validatoren dürfen nach Aktivierung nicht als vollwertige Consensus-Teilnehmer weiterlaufen
- keine Aktivierung allein per GUI-, RPC- oder Server-Schalter
- keine Abhängigkeit von CURA-/Developer-Servern

Grundsatz:
Release früher, Aktivierung später.
Validatoren und Nutzer erhalten vor der Activation Height eine deutliche Mandatory-Update-Warnung.

0.0.8.5 – QUANTUM-RESISTANT DATA-AT-REST & CRYPTO AGILITY
---------------------------------------------------------

QRX Drive muss Nutzerdaten von Anfang an so ablegen, dass ein späterer starker Quantencomputer heute gespeicherte Daten nicht trivial nachträglich entschlüsseln kann.

Ziel:
Schutz gegen "harvest now, decrypt later".

Vorgeschlagene Crypto Suite v1:
- Dateiinhalte: AES-256-GCM oder final festgelegter 256-Bit-AEAD-Modus
- Pro Datei/Objekt: eigener zufälliger 256-Bit File Encryption Key
- Key Encapsulation / Sharing: ML-KEM, vorzugsweise zunächst hybrid mit klassischem ECDH
- Manifest-/Ownership-Signaturen: ML-DSA
- besonders langfristige Recovery-/Root-Signaturen optional zusätzlich SLH-DSA
- Hashing/Merkle Trees: SHA-3 mit ausreichend großer Ausgabe
- Provider sehen nur Ciphertext

Ablauf:
User File
  ↓
Random 256-bit File Key
  ↓
AES-256-GCM Encryption
  ↓
Encrypted Chunks
  ↓
Erasure Coding
  ↓
Encrypted Shards
  ↓
Independent QRX Storage Providers

File Key:
File Encryption Key
  ↓
ML-KEM / Hybrid PQ Key Wrapping
  ↓
Encrypted Key Envelope
  ↓
Encrypted Manifest

TODO:
- qrx-drive-pq-v1 Crypto Suite definieren
- AES-256-GCM Data-at-Rest
- individuellen File Key pro Objekt
- ML-KEM Key Wrapping
- ML-DSA-signierte Manifeste
- optional SLH-DSA für Recovery-/Root-Artefakte
- SHA3-basierte Merkle Commitments
- Crypto-Suite-Versionierung
- Key Rotation
- Re-Wrapping ohne vollständigen Datei-Reupload
- PQ-sicheres Sharing zwischen QRX Wallets
- PQ-sichere Recovery-Artefakte
- Migration qrx-drive-pq-v1 -> spätere Suites
- Crypto Agility als Protokollpflicht
- Tests gegen langfristige Harvest-Now-Decrypt-Later-Szenarien

0.0.8.15 – QRX DEVELOPMENT TREASURY RULE
----------------------------------------

Storage Development Share:
STORAGE_DEV_SHARE_BPS = 50
= 0,5 %

0,5 % wird erhoben auf:
- neuen Storage Contract
- Storage Contract Renewal
- Storage Expansion auf den Mehrwert

Keine erneute Dev Fee auf:
- Proof Transactions
- Repairs
- Provider Replacement
- Shard Migration
- Settlement
- interne Storage-TXs

Grundsatz:
0,5 % auf den wirtschaftlichen Storage-Umsatz, nicht auf jede technische Storage-TX.

Empfänger:
QRX Development Treasury

Wallet zeigt die Gebühr transparent.

0.0.8.17 – USED STORAGE BEATS EMPTY STORAGE
-------------------------------------------

Belegter Storage muss deutlich stärker vergütet werden als ungenutzte Reservekapazität.

Prinzip:
1 TB used storage = 100 % economic weight
1 TB free proven reserve = nur kleiner Bruchteil

Damit finanziert QRX nicht dauerhaft ungenutzte Petabyte-Farmen.

0.0.8.56.1 – UNBOUNDED LOGICAL OBJECTS / HIERARCHICAL CHUNK INDEX
------------------------------------------------------------------

QRX Drive MUST NOT impose an arbitrary product-level file-size limit such as
2 GB, 100 GB, 1 TB or similar. Large files are logical objects composed of
bounded independently processable chunks.

Protocol rules:
- logical plaintext length uses uint64_t
- default chunk size: 8 MiB
- supported chunk range: 64 KiB .. 64 MiB
- hierarchical content-addressed 64-way index pages
- bounded-memory upload/download
- streamed restore
- each private chunk encrypted independently with AES-256-GCM
- one 256-bit file key per logical object
- file key wrapped using X25519MLKEM768 hybrid KEM
- SHA3-256 CAS integrity for descriptor, index pages and chunks
- per-chunk AAD binds object salt, chunk index and plaintext length
- P2P transfer remains range-bounded and resumable

There is no artificial QRX product cap on total object size. Practical limits
come only from uint64_t protocol representation, host filesystem limits, user
quota, available proven network capacity and contract economics.

0.0.10.32 – CONFIDENTIAL COMPUTE / FULLY HOMOMORPHIC ENCRYPTION (FHE) [ROADMAP]

Ziel:
QRX Drive und QRX Compute sollen perspektivisch Workloads erlauben, bei denen
geeignete Berechnungen auf verschluesselten Nutzerdaten ausgefuehrt werden,
ohne dass ein Compute-Provider den Klartext oder den geheimen
Entschluesselungsschluessel erhaelt.

Architektur:

Client plaintext
  -> client-side encryption / QRX Drive PRIVATE_PQ object
  -> FHE job envelope + ciphertext references
  -> QRX Compute provider executes supported encrypted circuit/model segment
  -> encrypted result + proof/commitment
  -> client-side decryption

Binding requirements:
- FHE ist zusaetzlich zur bestehenden clientseitigen QRX-Drive-Verschluesselung;
  normale Drive-Verschluesselung allein erlaubt keine Berechnung auf Ciphertext.
- Bevorzugt werden lattice-basierte, offen spezifizierte FHE-Schemata/Runtimes
  mit dokumentierten Post-Quantum-Sicherheitsparametern. Kandidaten wie CKKS,
  BFV/BGV oder TFHE sind erst nach konkreter Parameter-, Lizenz- und
  Kryptographiepruefung zulaessig; der Name eines Schemas allein ist kein
  Quantum-Security-Nachweis.
- Kein Provider bekommt den geheimen Client-Schluessel. Evaluation Keys werden
  minimal, jobspezifisch und capability-gebunden ausgegeben.
- Ciphertext, Evaluation Keys, Job Graph, chain_id, protocol/version und
  Input-/Output-Roots werden kryptographisch aneinander gebunden.
- Keine stille Fallback-Entschluesselung beim Provider. Nicht unterstuetzte Jobs
  muessen fail-closed bleiben oder ausdruecklich in einen nicht-FHE Modus wechseln,
  den der Nutzer separat bestaetigt.
- FHE-Jobs laufen im bestehenden Secure Execution Sandbox / Compute Job / Escrow /
  PoUC-Rahmen und erzeugen keine neuen QUB-Emissionen.
- QRX Drive speichert Ciphertexts und versionierte Content Roots; Revisionen
  bleiben immutable referenzierbar und kryptographisch pruefbar.
- Metadata Leakage (Dateigroesse, Jobdauer, Access Pattern, Modell-/Circuit-ID)
  wird separat modelliert; FHE wird nicht als vollstaendige Traffic-/Metadaten-
  Anonymisierung dargestellt.

Phased delivery:
1. FHE capability registry + benchmark harness + deterministic test vectors.
2. Encrypted scalar/vector demo jobs; client key lifecycle and recovery policy.
3. CKKS/BFV/BGV/TFHE candidate evaluation with audited security parameters.
4. Partial encrypted inference for explicitly supported model segments.
5. Hybrid confidential pipeline (FHE where practical, local execution where
   decryption would otherwise be required) with explicit user-visible boundary.
6. Only after independent cryptographic/security audit: production activation
   through normal QRX governance/readiness gates.

Acceptance gates:
- Provider never observes plaintext in an FHE-marked job.
- Secret key never leaves the user's trusted client boundary.
- Known-answer vectors match across supported architectures.
- Parameter sets have documented security estimates and minimum target security.
- Resource amplification (RAM/CPU/network/ciphertext expansion) is benchmarked
  and bounded before market quotes are accepted.
- Malformed ciphertext/evaluation-key fuzzing cannot crash provider/node/wallet.
- No downgrade from FHE to plaintext without explicit user consent.
- Result provenance/version roots remain compatible with QRX Drive revisions.

Status:
ROADMAP ONLY. No claim is made that 0.0.9 or current 0.0.10 source can already
run arbitrary AI inference fully homomorphically.
